# Backlog Task Ops

## Overview

Backlog運用で繰り返し発生する「一覧取得」「コメント運用」「クローズ運用」を安定化する。  
特に、出力省略が起きる大きな一覧をページングで欠損なく取得し、ユーザーがそのまま使える形式で返す。

## Default Scope

- デフォルト担当者IDは `636482` を使う。
- 未完了は `statusId: [1,2,3]`（未対応/処理中/処理済み）を基本とする。
- 完了は `statusId: 4` を使う。
- 一覧は `dueDate asc` を基準にする（期限未設定は先頭に出る想定）。

## Workflow 1: 担当課題の一覧化

1. `backlog_count_issues` で件数を確認する。  
2. `backlog_get_issues` を `assigneeId:[636482], statusId:[1,2,3], sort:\"dueDate\", order:\"asc\"` で取得する。  
3. 取得結果が長く省略される場合、`count` と `offset` で分割再取得する（例: 5件ずつ）。  
4. 結果は必ず「課題キー + タイトル（summary）+ 状態 + 期限」で返す。  
5. ユーザーが指定した形式（例: タイトル付き、未対応のみ、期限順）に再整形する。

## Workflow 2: コメント運用（下書きと投稿）

1. まずユーザー意図に沿ったコメント下書きを提示する。  
2. ユーザーが「投稿して」と明示したら `backlog_add_issue_comment` で投稿する。  
3. 投稿後は「どの課題に」「どの要旨で」記録したかを短く報告する。  
4. 投稿前に無断でコメントしない。

## Workflow 3: 課題クローズ

1. ユーザーからクローズ指示を受けた課題に対して `backlog_update_issue` を実行する。  
2. ステータスは `statusId:4`（完了）を使う。  
3. 必要に応じてクローズコメント（例: 一旦完了、必要時再オープン）を `comment` に含める。  
4. クローズ後、残課題一覧を再取得して最新状態を返す。

## Output Rules

- 一覧は情報欠損を避けるため、長い場合はテーブルまたは箇条書きで分割出力する。
- ユーザーが「タイトルも」と言った場合は `summary` を必ず表示する。
- 期限未設定は「未設定」と明示する。
- 件数変動が発生した場合（新規課題の割り込みなど）は、最新件数を明記して説明する。

## Safety Rules

- コメント投稿・ステータス更新は、ユーザーの明示指示がある場合のみ実行する。
- 課題キー指定が曖昧なら、実行前にキーを確定する。
- 既存コメントの上書きや削除は行わない（依頼がある場合のみ別途対応）。
